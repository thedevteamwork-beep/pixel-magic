# Projects (AI Influencer first) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add per-user, typed projects to the backend, let jobs belong to a project, and move the AI Influencer page from `localStorage` and a simulated preview to these APIs.

**Architecture:** Two pieces change, and generation itself does not:
- A new `app.projects` table, plus a nullable `jobs.project_id`. Valid project types come from a code registry (`src/projects/registry.ts`) that checks each type's `data` with Zod.
- Jobs keep all generation state, and `POST /v1/jobs/:plugin/:operation` accepts an optional `projectId`.
- The influencer page creates a project on its first Generate, then creates and polls ordinary jobs inside it.

**Tech Stack:**
- Backend: Express 5, Knex and Postgres, Zod 4, Vitest with supertest (real test DB).
- Frontend: Next 16, React 19, Vitest (node environment).

**Spec:** `docs/superpowers/specs/2026-11-14-projects-design.md`

## Global Constraints

- Follow `backend/AGENTS.md`:
  - SQL only in `src/db/repositories/*.repo.ts`;
  - tables through `T` (`src/db/tables.ts`);
  - timestamps from `deps.clock.now()`, passed into repos;
  - errors as `AppError(status, code, message)` with existing codes only;
  - ESM imports end in `.js`.
- Node 22: `export PATH=~/.nvm/versions/node/v22.23.4/bin:$PATH` before any npm or npx command.
- Backend tests need the test DB on `localhost:54329`: `cd backend && npm run db:up` once. `globalSetup` migrates it.
- Zod: `z.strictObject` for every body. Panel routes sit behind `requireUser` and `ensureUser`.
- A project that is missing or belongs to someone else returns `404 NOT_FOUND` on every route.
- Limits:
  - `title`: trimmed, 1 to 120 characters.
  - `GET /v1/projects`: `limit` 1 to 50, default 20.
  - AI Influencer `traits.*`: max 40 characters.
  - `extra`: trimmed, max 500 characters.
  - `archetypeId`: max 60 characters.
- The job request hash includes `projectId` **only when it is sent**.
- Lock order in `createJob`: profile, then project (`FOR UPDATE`).
- `DELETE /v1/projects/:id`: unlink the jobs first, then delete the row, in one transaction.
- Frontend: follow `frontend/docs/folder-structure-and-css.md`:
  - images only through `ui/Media`;
  - feature constants in `components/ai-influencer/constants.ts`;
  - pure helpers in `src/lib/ai-influencer/`.
- **No commits.** The user commits and pushes themselves. Where a task would commit, stop and report instead.
- Gates:
  - backend: `npm run lint && npm run typecheck && npm test`;
  - frontend: `npm run format:check && npx tsc --noEmit && npx eslint . && npx vitest run`.

## Review Focus

1. **A `projectId` that is valid but belongs to another user** on job create: `404`, no job row, no credit reserved. Covered in Task 5.
2. **A retried job create (same key) after the project was deleted** returns the original job (`200`), not `404`, because the idempotency lookup runs first. Covered in Task 5.
3. **An old client with no `projectId`** keeps the same request hash, so an existing idempotency key does not suddenly return `409`. Covered in Task 5.
4. **Deleting a project with completed jobs** keeps the jobs, their outputs and credit ledger rows, and they still list in `GET /v1/jobs`. Covered in Task 3.
5. **A `204` from `DELETE`** must not crash the frontend client (`response.json()` on an empty body). Covered in Task 6.
